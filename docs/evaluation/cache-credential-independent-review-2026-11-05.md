# Independent cache credential source review

Source-only review of root's initial correction during the PERF01 quiet window. No test, build or browser command was run for this review; the source changes were not yet verified after implementation. Root's preserved baseline is10 failing cases and2 passing controls. This document is a dated review of the first correction, not final acceptance of later revisions.

The extraction avoids a circular import: auth depends only on cache storage; the request helper depends on auth and storage. `defer` captures generation at subscription, authoritative HTTP responses no longer fall back, and old-generation successes/errors are rejected before a cache write/fallback. The v2 namespace ignores subsequent legacy-writer responses. Draft/source namespaces are untouched. The imperative counter holds no credential history. Existing status0/non-HTTP fallback compatibility is explicitly retained rather than mislabeled as proof of offline authenticity.

## Findings sent to root

1. **Deferred cross-tab event window.** The global API-key storage changes synchronously in another tab, but the receiving tab's storage event is queued. Before that event runs, a pending A response can pass the unchanged local counter and emit/write into v2 while B is already the current stored credential. A B status0 request can then read A's value. A generated regression can represent this scheduling by changing localStorage without immediately dispatching the storage event, releasing the old Subject, performing the new offline read, then delivering the event. Request-scoped current-credential comparison can fence the ordinary window without persisting/logging/naming keys. A shared nonsecret opaque mutation ticket can additionally fence an updated-tab cross-tab A→B→A cycle completed before either event is delivered. Local generation remains useful for in-tab ABA. Legacy writers lacking a shared ticket require an explicit bounded compatibility statement; never silently claim full cross-tab ABA coverage from an equality check alone.
2. **Denial followed by older success.**401/403/404 clear entries but do not advance the pending-read epoch. An older same-credential success can refill the cache after that authoritative denial; a later status0 fallback can return it. This no longer converts the direct denial into success, but it weakens the intended cache-authority invalidation. Root should decide whether denial fences all previously admitted reads, using a separate authority epoch rather than falsely announcing a credential change. Proposed exact ordering: subscribe old Subject → current401 → old success → status0 fallback. No such case appears in the initial12 tests.

Both findings are source-derived scheduling cases, not executed regressions or observed production exploitation. Root retains implementation and acceptance ownership.

## Subsequent v3 source review

During the later short CPU hold, root's new v3 design adds owner-SHA metadata and a shared opaque authority revision. Request checks compare the active captured credential, local generation and shared revision synchronously; cache envelopes must match both owner and revision. `clearCache` advances/fences authority before removal. The three actual cached ApiClient HTTP reads pin the captured credential using HttpContext, and the interceptor removes contradictory authorization headers. HTTP subscription starts immediately rather than waiting for SHA computation; unavailable cryptographic binding disables persistent cache/fallback. The import graph remains acyclic and no draft key is cleared. These source changes address the earlier ordinary cross-tab and updated-setter ABA/refill findings, subject to regression verification.

One additional ordering issue was sent to root: the first v3 `catchError` awaits the owner-digest Promise before classifying/fencing an authoritative401/403/404. A held digest delays invalidation after the HTTP denial has arrived, allowing another current-scope request whose digest already resolved to emit/refill or fall back during that window. The denial path needs no owner digest and should establish its fence before that await. Proposed controlled case: hold the denial's digest; deliver401; then release an older successful request or status0 read; verify it is already fenced before completing the denied digest. This is source-only reasoning, not an executed failure. Root owns the correction/tests and final acceptance.
