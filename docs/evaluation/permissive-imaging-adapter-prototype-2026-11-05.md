# Permissive Imaging adapter prototype — 2026-11-05

Status: isolated research/proof, **not adopted**. Production Imaging still references ImageSharp 3.1.11. The earlier AI-only PNG replacement does not resolve this remaining dependency or its advisories. No fitting, corpus accuracy study, real provider call, or source-manuscript change is part of this work.

**Open validation finding:** the frozen v9 native JPEG traversal accepts two independently generated malformed/recoverable streams (SOS header with no entropy and one-third entropy followed by EOI). Full native `GetPixels` also reports success. The old ImageSharp target-size validator accepts both, so this is not a demonstrated compatibility regression, but the earlier strict-completeness claim is withdrawn. Native traversal/decodability does not prove that every JPEG entropy-coded pixel was present. Root approved preserving this known recoverable-JPEG compatibility under a bounded first-frame decodability contract. These two observations are not strict-refusal passes; archive migration still requires the remaining resource and functional gates.

## Scope and ownership

No upstream build script was executed.

## Evidence preserved before each correction

- Original strict v2 comparison retained 169 failed operations across 22 files. Lossless tolerance was not widened.
- The evaluator identified pre-existing PNM binary-delimiter and 16-bit endian/scaling errors. Named source-byte oracles were approved before candidate comparison; later P4/Group3 exceptions are explicitly recorded as approved **after observation**. Unseen holdouts remain separately registered.
- v5 original matrix: 1,221 comparisons passed, 21 failed, all failures in three associated-alpha 16-bit TIFF files. Extension: 614 passed, 68 failed, limited to five BigTIFF-MM refusals and four associated-alpha 16-bit tiled files.
- Associated-alpha correction quantizes each associated 16-bit channel to the nearest byte and stores premultiplied BGRA directly. The independent actual-Skia probe matches the original 187 pixels and three unseen 8,192-pixel grids covering every byte alpha value. A Python unpremultiply approximation did not match Skia's tie handling; that failed approximation is retained, not substituted for the native probe.
- Two successive BigTIFF endian hypotheses failed all five unchanged inputs. The cumulative third correction handles raw header version, unsigned 64-bit entry counts before casting, and 1/2/4-byte inline-slot extraction. The new registered fork proof opens and decodes all five files with unchanged source/input hashes. This is an open/decode control, not a claim that the complete pixel/resource matrix has passed.
- Valid 256/4,095/4,096-tag inputs exposed unbounded default managed warning output. The independent watchdog terminated processes after more than its 64 KiB stream budget. Native libtiff accepts the same sorted inputs quietly. v6 enables upstream `THREAD_SAFE_LIBTIFF` and provides a per-instance sink: counts all basic warning/error callbacks, retains at most eight 256-character method/template summaries, never formats untrusted arguments, and does not change global logging state. Extended callbacks are not double-counted.

## Frozen v6

`candidate-v6-registration.json` pins 204 source/build files before independent evaluation. The associated-alpha correction, BigTIFF fork and per-instance diagnostics are frozen. Primary Skia `Dimensions` and scanline `DecodeBand` use a bounded view of one file handle; they do not first copy the full encoded source. The source-length guard admits at most 512 MiB, refuses truncation/growth, and preserves original encoded checksums where returned. Same-length hostile file rewrites and filesystem races are not globally eliminated.

The prototype has deliberate proposed metadata limits: 4,096 tags; 16 MiB per tag; 32 MiB aggregate metadata; one million segments; 64 MiB encoded and 512 MiB decoded per segment. These are policy proposals requiring review, not an unnoticed redefinition of production format compatibility. A separate sparse-file/stream probe proves the encoded length boundary without allocating a 512 MiB test array.

**Remaining resource gaps:** TIFF bounded preview and band paths still decode the full frame. Fallback `Dimensions` still snapshots the admitted encoded input. Neither is a streaming-region or hard total-RSS solution. Existing `DecodeBounded(maxPixels: 1)` can overshoot the requested budget through integer rounding; it is a separately registered pre-existing bug, not a relaxed evaluation threshold. Native scratch memory and synchronous decode time are not hard bounded by these guards.

Build receipts disclose the existing upstream CS8981 lowercase-type warning. One offline build also reported NU1900 because vulnerability-feed access failed; that build is not a clean security audit.

## JPEG TIFF diagnosis and separate v7 experiment

The baseline refuses certain JPEG/YCbCr tiled additions. Managed IJG output differs from two independent libtiff references by RGB maxima 71/76, well outside the pre-registered JPEG maximum 2 / mean 0.5 policy. These remain unvalidated additional capabilities. Native libtiff source disproves the initial simple fancy-upsampling toggle hypothesis for the RGB path.

A separately registered diagnostic reconstructs original TIFF JPEG tables and tile streams and passes them through existing Skia: both q50/q95 images match the independent Pillow/libtiff reference exactly. Its initial launcher stalled and was stopped; the explicit single-node, nonshared build and direct harness then exited zero. The registration pins source/inputs; new harness binary hashes are explicitly a **post-execution** receipt. It is not described as a pre-registered binary measurement.

Root approved an isolated v7 per-segment JPEG7 branch for contiguous 8-bit, three-component RGB/YCbCr only. It validates table/marker lengths, exact SOI/EOI, SOF precision/components/dimensions and codec dimensions before tile allocation; requires complete successful pixel decoding; preserves raw orientation and original TIFF checksum; and never falls back to the known-different IJG result if an eligible segment fails. This branch is not yet accepted or adopted. Unseen q82 and malformed nested-frame cases must be evaluated independently.

## Later frozen slices: v7–v9

v7 adds the separately approved JPEG7 segment branch. v8 adds streaming fallback metadata: shared TIFF first-IFD offset/count checks use a bounded seek reader, PNM headers scan tokens/comments without buffering them, and TGA/QOI validate fixed headers/source extents. These versions and their registrations are immutable. Large interleaved TIFF offset/count tables may still be a seek/I/O stressor; that is a registered independent hypothesis, not a demonstrated failure or a claimed solution.

v9 adds `ImageDecoder.ValidateEncodedSnapshot(byte[] bytes, string scope)`, returning immutable format/dimension/strategy evidence. It traverses the supplied snapshot through the selected decoder without opening the scope as a path; the JPEG finding above limits any strict-validity claim. A registered generated prior-nine probe accepts all nine formats with unchanged arrays. BMP/JPEG use all scanlines; PNM/TGA/QOI validate all raster/opcode data without an output image; PNG/GIF/WebP use full native first-frame destinations; TIFF uses a full first-frame destination and rejects decoder error diagnostics. The bounded scanline validation buffer holds at most 32 rows; on a small image it can geometrically cover the whole image, while remaining a row-validation buffer rather than a requested full-frame codec destination.

`AllocatedFullRasterDestination` distinguishes these strategies, not total native allocation, resident memory or decode time. **A full destination does not by itself demonstrate a regression against the old ImageSharp `TargetSize = 1` implementation**; the old decoder's actual allocations must also be measured. Full-destination branches remain unqualified for archive migration until that comparison and malformed-late-pixel controls pass or an explicit policy is approved. The existing archive caps of 25 MiB per image and 250 MiB aggregate remain the application's responsibility and are not changed by this prototype.

The current v8 original-166 comparison passes all **1,242** comparisons. The independent evaluator identified one remaining BigTIFF-MM associated-alpha exact-pixel mismatch (29 bytes, maximum delta 2), despite successful open/decode. Root subsequently approved the narrow canonical/source-equivalence policy, with four unseen LE/BE controls passing all8 operations (32 passes). The original21 strict differences remain recorded; no generic tolerance relaxation or silent compatibility workaround is approved. Extension, new-validation and resource outcomes remain pending.

A source-only PNG streaming-validator design was considered using the [dated W3C PNG Third Edition recommendation](https://www.w3.org/TR/2025/REC-png-3-20250624/). No such parser was implemented: first measure whether the resource comparison requires it, before adding IHDR/chunk/CRC, zlib, all filter types, low-bit palettes, Adam7 and APNG first-image maintenance obligations.

The isolated fork footprint is **153 vendor C# files / 65,048 lines / 2,818,482 bytes** in the current patched source, with semantic edits in three vendor files plus two owned build/version files. The complete upstream license bytes remain identical. `fork-v4-footprint.json` records these quantities. This is a material vendoring/maintenance commitment even though the behavioral patch is narrow; a production decision must account for maintaining the entire older managed TIFF/JPEG/compression implementation, not describe it as a tiny standalone TIFF parser.

Snapshot API integration contract: the caller retains an immutable `byte[]` for the call; the helper does not clone, write, reopen or return those bytes. It does not replace the application's narrower archive byte caps. Streams rejected by the selected decoder return `LeviathanException` with `RejectedArchive` and reason `invalid-image-snapshot`; recoverable malformed JPEG can still be accepted as documented above; size admission uses the existing size-limit contract. Null arguments retain normal argument validation. Out-of-memory failures are not disguised as successful validation or ordinary format rejection. `SKCodecResult.IncompleteInput` is rejected, unlike the separate historical preview behavior. First-frame validation is distinct from validating every animation frame. The raw source bytes, rather than any derivative or validation bitmap, remain the bytes the application should export.

No existing model weights, preprocessing profiles or manuscript data are rewritten. Approved source-correctness exceptions deliberately change pixels for their named legacy PNM/Group3 cases; synthetic pixel evidence is not proof that predictions of every existing model remain unchanged on those formats. No natural-text recognition, model compatibility study or corpus accuracy claim is made. The primary Skia path's unchanged implementation and generated parity controls do not replace those later gates.

NuGet auditing limitation: the later source fork is a project reference, not an indexed NuGet package. A zero-advisory package report therefore does not assess that fork or establish equivalence to patched native libtiff/libjpeg releases. Source provenance, independent malformed/resource tests, manual upstream security monitoring and the explicit maintenance owner remain separate obligations.

## Frozen v10 budget correction and v11 TIFF band prototype

Root approved the independently frozen [strict returned-pixel policy](strict-decoded-pixel-budget-proposal-2026-11-05.md). Isolated v10 rejects nonpositive budgets before source decoding, while preserving the existing missing-path error priority. It changes only outputs that would exceed the requested pixel count: floored uniform dimensions plus an integer long-axis clamp; the fallback source is resampled once, and an oversized native minimum-scale intermediate is resampled once with its existing color/alpha representation and linear sampling. Already-in-budget legacy output is unchanged. Five literal/derived oracles were frozen before evaluating v10. This bounds returned pixels, not native intermediate size or temporary decoder memory. Independent results remain pending.

Isolated v11 adds TIFF `DecodeBand` from the same admitted read-only file handle, avoiding the full encoded TIFF snapshot and skipping irrelevant strips/tiles. Existing palette/16-bit and native-JPEG paths clip destination writes to the requested raw-frame band; remaining TIFF forms use per-strip/tile RGBA conversion. The original top/height clamping remains. The equivalent unsigned-default one-strip height is normalized only in memory to avoid signed overflow in the upstream convenience wrapper. Source bytes are not changed.

A band still needs the largest intersecting source segment's decoder workspace. A source containing one image-sized strip can therefore require image-sized workspace, and generic bilevel conversion uses a four-byte-per-pixel RGBA block even when the encoded samples use fewer bits. No universal constant-ROI, 512 MiB total-process or synchronous timeout claim is made. TIFF bounded resize remains a full-frame path. ROI decoding validates the selected blocks; it is **not** a whole-first-frame archive validator and may not inspect corruption confined to an unused block. The separately qualified snapshot-validation API remains necessary for archive export. v11 independent pixel/source/resource controls are pending; no production format/dependency change is authorized by these prototypes alone.

An eventual source-fork adoption also needs an explicit third-party source-component inventory and distributed notice entry binding the pinned source/license/patch/version to the published assembly hash. A NuGet-package-only collector may omit a project reference; its successful execution would not substitute for this record. No production notices collector or package has been changed here.

Root-approved v12 qualifies only the snapshot API documentation, mode labels and failure text: native first-frame **decodability** by row traversal or raster decoding; owned first-frame raster walking; TIFF decoder acceptance. It preserves both known recoverable JPEG cases exactly. Neither an EOI check nor full native `GetPixels` repairs the strict-completeness claim: the registered full-raster diagnostic returns `Success` for both negatives and the valid control with unchanged source/input/binary hashes. No entropy decoder, acceptance weakening or removed format was introduced to hide the finding. Prior v9 labels/claims remain historical evidence, not the current contract.

Independent v8 metadata-only results establish the actual tradeoff: admitted sparse 512 MiB−1 PNM/TIFF inputs identify correctly with 8,776/10,464 managed bytes allocated; the over-cap sparse input is refused before source-sized allocation. A 32 MiB PNM comment uses 8,776 bytes but takes 404 ms versus the old 38 ms. The valid 562,500-segment shared-tile TIFF uses 10,344 bytes versus the old 40.58 MB, but takes 457 ms versus 35 ms. All owned subprocesses exit zero with unchanged sources and no raster decoding. These observations establish bounded managed allocation on those cases, **not performance parity**; a bounded metadata cache/token-buffer proposal is under review. Receipts: independent `runs/dimensions-baseline` and `runs/dimensions-v8`.

Source provenance qualification: the cached 2.4.660 nuspec provides no repository-commit field. The verified official Git tree establishes the identity of the copied source, not a reproducible source-to-published-2.4.660-binary attestation. The prototype's `2.4.660-leviathan.*` identity labels this experiment; the exact Git commit and cumulative patch are authoritative. A production component/version decision must not imply an upstream binary correspondence that has not been established.

The v10 budget correction also has an independent [narrow production backport proposal](decoded-pixel-budget-backport-2026-11-05.md), retaining ImageSharp and all other decoder behavior. Its artifact-only matched tests fail9/pass5 before and pass14 after; the main runtime file remains unchanged pending review. This useful correction does not depend on accepting the TIFF fork.

## Deferred new grayscale-alpha capability

Eight new two-channel grayscale-alpha controls are refused by the old ImageSharp path but accepted by v13. Independent diagnostics find dropped alpha or incorrect color in several of these new accepts; therefore this is an unvalidated **new capability**, not a demonstrated regression of an existing accepted variant. Root selected explicit deferral rather than guessing a normalization rule. Source-only v14 adds a typed unsupported-variant refusal for MINISBLACK/MINISWHITE, two samples, recognized associated/unassociated alpha across pixel decoding/bounded/band/snapshot routes. Metadata dimensions remain readable. The draft was not built during the quiet window. After release, the independently frozen v14 build passes40 exact typed refusals,45 known-format accepts and17 metadata/source-identity controls. The v13 wrong-pixel observations are retained, and no grayscale-alpha support claim is made.

The independent archive metadata probes partially test the concern that native codec creation could expand compressed metadata differently from old `SkipMetadata=true`. Both validators accept the frozen 1/16/64 MiB ICC cases. For the 16 MiB case, measured managed allocations are 33,636,184 bytes old versus 26,232 new, with sampled process peaks about54 MB for both. The 64 MiB case also completes within the owned limits, but that fixture is a header-shaped incomplete ICC profile (tag count0 and zero illuminant), not a full valid color-transform workload. These specific results do not establish a general metadata-allocation regression or a universal native metadata bound; sampled peaks and the exact generated profile contents limit the conclusion. Raw results are in independent `archive-validation/metadata-comparison.json`.
