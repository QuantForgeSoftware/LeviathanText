## Journal capacity and responsiveness: source-only follow-up

The current deliberate append-only contract has finite capacity:512 records per exact scope,4MiB aggregate bytes,2MiB per record and2048 total storage keys. Text input saves a new snapshot, while successful/resolved snapshots remain journaled. A sufficiently long session therefore reaches explicit persistence refusal and retains only its mounted newest work until an explicit recovery/export/compaction workflow exists. This is a known safe-refusal/capacity limitation, not evidence that old records were deleted or that mounted work was safely persisted. Increasing caps or automatically removing old records would require a separate ownership/concurrency policy.

Source reading also identifies repeated bounded work: save scans existing entries, invokes load for current-tip validation, then invokes load again after publication. Each load currently traces each record's ancestors independently. No timing or user-visible latency conclusion follows from that source complexity. A future generated study should freeze exact store and fixture hashes; test sequential histories at1/32/128/256/511 records and small/large snapshots; distinguish serialization, storage IO, scan and lineage verification; retain exact recovery/base/undo/receipt parity; and stop on explicit quota rather than dropping records. Browser main-thread responsiveness should be measured separately from a pure in-memory recording-storage run, with fixed input cadence and explicit host/runtime. No such benchmark was executed in this review.
