# Worker heartbeat follow-up

This is an unimplemented source-review brief, not an automatic-heartbeat claim. PERF-01's retry-safe backoff adoption does not close this work. Current `WorkerHost.RunNext` executes a synchronous handler; no production caller invokes `Heartbeat`. Polling excludes Running jobs even after expiry, so expiry alone does not cause automatic competing execution. Explicit `TryClaim` recovery requires the previous handler to have stopped. Preserve that safety rule.

Before introducing automatic renewal, specify a per-attempt identity `(jobId, workerId, claimId)` and require all three in every renewal. The existing public heartbeat checks worker ID only; do not reuse that weaker seam as a timer callback. A late callback from a previous claim must not renew a newer claim even if the worker ID is unchanged. Cancellation/finalization must stop and join the renewal loop before publishing terminal status, without converting a committed handler side effect into an automatic retry.

Do not start a Timer against the current shared LocalStore connection or test dictionary. `IJobStore` has no concurrent-use contract; the production adapter wraps a LocalStore whose connection is also used by the handler. Design an independently owned durable connection/session for renewal or a serialized cooperative seam with explicit guarantees. A blocked synchronous model call cannot provide a reliable cooperative heartbeat by merely calling between pages. Choose and document the behavior for lost ownership, renewal failure, long model calls, process pause and administrative cancellation. Do not automatically reclaim an expired Running job while its old publisher may still execute.

Required generated regressions before adoption: current claim renews; wrong worker/claim/terminal status refuses; late old-attempt renewal cannot touch a new claim; cancellation and finalization race with renewal without resurrecting a job; API cancellation remains authoritative; independent durable connections serialize safely; renewal failure is observable and cannot silently duplicate publication; all owned background work stops on handler exception and process shutdown. A bounded multi-process proof must retain exact attempt/output IDs and lease clocks and preserve existing retry cadence. Register resource overhead separately; no fitting or natural labels are necessary.
