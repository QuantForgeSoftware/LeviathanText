# Proposed owned recovery-journal responsiveness study

This is source preparation, not an executed benchmark or a claim that the current editor is responsive. Main's append-only journal deliberately preserves every old record. Its 512-record and4MiB scoped aggregate bounds can eventually refuse persistence. The mounted text must remain visible and persistence failure must be explicit; automatic deletion or compaction is outside this study.

Proposed stage A uses the actual public WorkspaceDraftStore in a new private headless browser profile with empty native localStorage. Fixed cohorts contain64,512,4096 and16384 generated Greek scalars, a true unchanged base/revision, two fixed-shape undo entries, and one extra scalar per edit. Attempt at most520 ordinary edits, with up to eight further attempts after the first refusal (absolute528-attempt cap). Each cohort has a60-second wall cap. Check the exact unique saved tip/text after every save; a refusal must not be reported as success, and all old admitted bytes must remain. Record every save/load duration, record count, encoded key/value bytes and first refusal.16.7ms/50ms flags are descriptive preregistered markers, not inferred application acceptance or universal performance limits. No adaptive cohort or policy-limit changes.

Source-only harness: `.artifacts/experiments/workspace-journal-study-v1/run-store-study.ts`. It refuses nonempty storage, has no automatic entry point, never clears a whole storage area, and returns exact owned keys for later cleanup in its new profile. Source closure and actual compiled/browser binaries must be registered before execution. The harness has been compiled and strictly typechecked during preparation; no timing loop has executed.

Proposed stage B separately measures the actual current LineEditor through128 fixed generated input events in an isolated generated API/browser fixture. Record handler-to-next-animation-frame delay and long-task/event-loop observations while checking current draft/base/undo and recovered last-confirmed tip. This stage must first define exact generated profile/project/line identity, source/binary hashes, fixed sequence, receipt checks and owned-process cleanup; the store-only numbers cannot stand in for editor or cross-tab correctness. No component private fields, bypassed authorization, real images, models, fitting or provider calls.

Root must approve a finite sealed protocol and coordinate a CPU-quiet observation window before either timing stage. A future optimization requires a separately frozen candidate and unchanged bytes/recovery/error oracles; this task authorizes no compaction or production change.

The prepared store harness passes strict TypeScript checks and esbuild bundling. Two admission controls reject nonempty storage and unknown cohort sizes before any storage access or timing loop. ## Actual preparation controls and interpretation

The generated API seeder and isolated API publish build successfully. Compilation disables NuGet audit for reproducible offline build preparation; this is not a new security advisory audit. The first seed used default optional line FrameRef/RegionId, which serialized as invalid `col-` identifiers and failed actual NativeJson reload; the failed SQLite store/log/source remain preserved as a separate product hypothesis. Version2 uses explicit valid capture/region/frame IDs with an empty image location. There is no image file or decode: any preview must be an explicit422 refusal, not a fallback. Version2 Save/Load and separate read-only store inspection return byte-identical native JSON before registration.

Stage B generates128 fixed trusted input events and captures mounted text externally before its untimed reload. If the journal policy refuses a later persistence attempt, the mounted full draft must remain with an explicit warning. The reload must recover exactly the last CONFIRMED durable tip, which may lag the mounted text; record that limitation, never claim the newest text recovered. Before replacing the generated mounted component, its complete text and final durable snapshot are saved in receipts. Public Undo must restore the prior entry from that persisted stack. No user work participates, and no server revision is saved. Last-confirmed restoration and persistence-failure visibility are separate from latency observations.

All integrity checks, record-byte comparison, storage-byte enumeration, CDP progress transport and durable-tip verification occur outside the recorded save/load intervals; they still contribute to whole-visit wall/CPU and observer overhead. Stage B capture-phase input-to-rAF includes the actual component event handler and browser scheduling, not CDP round-trip latency. The fixed observer emits long-task entries only if supported. The study is one descriptive baseline, with no comparison, inferential statistics or speedup claim.


## Pre-registration cleanup review

Independent source review found three harness defects before any measurements: stopping an already-exited root could miss its orphan descendants; failed spawn events lacked handlers; one teardown failure could prevent other cleanup and the final receipt. These are corrected in the separate owned-process helper. Ownership is witnessed by original detached root start identity and tracked descendants, retained after root exit; signals target only freshly verified exact PID/start identities. Cleanup verifies no remaining owned tree, handles spawn errors, and continues across every child/server teardown error. Two native FUNCTIONAL controls passed: intentionally missing executable, and a root exiting while its live descendant remains; the descendant was subsequently cleaned and no process remained. These controls ran no browser/study loop.

Each dedicated profile is removed only after owned process/server cleanup and receipt capture. A failed visit first archives only its generated localStorage LevelDB files, bounded32MiB, then removes that owned profile. Unexpected paths, oversized evidence or uncertain process cleanup leave an explicitly quarantined owned profile and failed receipt; no broad path removal or foreign-process signals. External cancellation follows the same finally cleanup. All orphan/spawn/control receipts stay separate from latency results.

Unexpected journal schema/lineage/verification refusal reasons stop the study after preserving their progress row; ordinary `journal-full` and generic native storage/serialization refusal remain explicit observations. The latter is never automatically relabeled quota exhaustion. No actual measurement has run at this registration-preparation point.


The final preparatory host controls exercised actual published `/me` (exact generated account/namespace), project reload, explicit metadata-only capture preview422, and `/ui/`200. All four passed, with no browser or study loop; the owned host exited and no descendants remained. All child working directories now point to the fresh owned temporary root, and child environments use only required process-path/home/tmp/.NET entries plus explicit generated host configuration. The earlier unexecuted registration is preserved as historical.

An independent outer launcher observes the controller's owned descendants and enforces the540-second observation deadline even if the controller's event loop stalls. Prelaunch integrity/admission checks occur before that deadline starts; the controller's own integrity check, readiness, observations and normal closure are inside it. On expiry/cancellation, exact owned processes are terminated and cleanup/proof finalization follows; do not describe the540-second observation cutoff as an instantaneous OS-level bound on cleanup or native work. The controller also has its own deadline and per-visit tree watchdog. Both retain failed/partial receipts and verify no owned descendant remains. The protocol is not approved for dispatch until the new final root binding and quiet GO.
