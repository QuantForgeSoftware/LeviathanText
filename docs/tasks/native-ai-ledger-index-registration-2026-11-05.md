## Candidate and exact scope

New owned evidence root: `.artifacts/experiments/perf02-ledger-index-v1/`. `source-registration.json` identifies baseline production SHA-256 `c58da0748fe022dcca19ef00bc1b0db73ff06b0b0f5b84f13c7cc975002b0e54`, copied baseline/candidate service files and `candidate.patch`. This is a source proposal, not a published/runtime manifest. Regenerate a new registration, without overwriting this one, if root's approved baseline differs.

`ReadLedger` currently resolves each issued source by traversing native revisions, lines and ownership, and resolves each receipt by traversing object/surface, local revisions and annotations. If all these histories grow together, repeated lookup traversal is quadratic. Attachment JSON parsing, UTF-8 size/checksum, source equality and receipt evidence digest work also recur, but remain required.

The isolated candidate changes only `NativeAiProposalService.cs`:

- Create one private `RequestHistoryIndex` per `ReadLedger` call. It is never a service field, static cache, DI singleton or stored result.
- Lazily index global revision locations, object-ID counts, owner-local surface-ID counts, global line-ID counts, local line/revision/annotation matches. Each identity holds its **first reference plus count capped at two**. Container dictionaries use reference identity, never native record structural equality/hashing. Memory is linear in encountered graph identities; these are temporary indexes, not a claim of constant memory or lower RSS.
- Preserve validation phases. Source missing/ambiguous checks precede text, local line ownership, object/surface/global-line ownership and layer checks in the same order. Missing unrelated data is not eagerly inspected merely because an index class was instantiated. Duplicate IDs are counted and rejected only at their existing referenced validation point. Receipt revision/annotation counts remain **surface-local**; an unrelated same ID on another surface is not newly rejected.
- Retain the already validated source reference in the private issued entry, allowing receipts to reuse its uniquely validated surface. This removes repeated `Single` owner/surface searches without granting new authority.
- Keep **every** attachment size/checksum/contract parse, version/ownership/source equality, proposal/range, duplicate issued/receipt, acceptor, revision/annotation field and serialized evidence digest check. No digest substitutes for exact canonical source equality. The first candidate has no serialization/digest cache.

Public signatures, saved schema, issued/receipt format, history content, optimistic save and authorization boundaries are unchanged. `Prepare` and the bounded acceptance plan's generic current-source/current-L2 scans are deliberately unchanged. This candidate targets `ReadLedger` lookup traversal; it does not eliminate whole-project loads/serialization, JSON parsing or all other history-dependent work. No persisted validation cache, schema migration, history truncation or source/label modification is proposed.

## Growing-arm identity and checksum parity: explicit decision required

Fixed replay arms allow byte-exact unchanged native comparison. New HTTP issue/accept calls generate proposal, L2, annotation and receipt identities/timestamps independently. Therefore cross-variant growing graphs cannot be compared by blindly removing IDs/hashes, nor by the old selected-field inspector.

If root approves growing-graph canonical comparison, preregister a bijective mapping from each **observed cycle's returned** proposal/L2/annotation/receipt IDs to stable cycle symbols. First validate original attachment bytes/SHA, receipt-to-issued hash, revision/annotation hashes, source/range/ownership and every cross-reference using the authoritative service. Then apply the ID/time mapping to **known typed records only**, including nested authoritative attachment JSON and their names/IDs, retaining every other field. Recompute comparison-only canonical content digests consistently and preserve the original hashes in raw evidence. Existing prefix IDs stay unchanged. Reject unmapped/generated collisions, canonical symbols colliding with original IDs, multiple mapping targets, broken links or unexplained differences. Preserve unknown fields/roles byte-for-byte or structurally unchanged; their differences remain visible rather than being dropped. New IDs must retain the registered production framing and new digests must be lowercase 64-character SHA-256 strings before comparison-only normalization. No substring-wide ID replacement or unchecked digest normalization is permitted. This transformation and a tamper/error test matrix must be independently reviewed before six-hour execution.

Alternative deterministic-ID application harnesses can avoid that mapping, but they isolate the service and are **not** the same API/DI/provider/SQLite resource protocol. If identity normalization or the full runtime/telemetry gate cannot be completed in time, stop at honest source/functional/short-probe evidence or register a clearly smaller campaign. Do not call a shortened or application-only run the completed24-visit protocol.
