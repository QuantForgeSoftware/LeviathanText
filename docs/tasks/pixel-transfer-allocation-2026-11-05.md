# Isolate fallback pixel-transfer allocation

The independent6MP resource comparison shows approximately1.10GiB allocation churn and2.7seconds in both old and owned QOI decoding; old TIFF fallback has similar churn. Both implementations call `SKBitmap.SetPixel` for every output pixel. Root is investigating whether the repeated temporary pixmap wrappers explain this cost. This is a hypothesis, not an established cause or production change.

Prepare a Skia-only generated probe with the existing exact4.153.1 package/native closure. Compare old SetPixel against one owned PeekPixels/span and native `SKPMColor.PreMultiply`, writing explicit BGRA bytes. The cached SDK documents SKPMColor's configuration-dependent layout; do not reinterpret its raw integer as fixed BGRA or invent premultiplication rounding. Preserve alpha quantization through the existing native conversion. Handle stride and lifetime explicitly; no borrowed span may outlive its bitmap/pixmap. First compare exact stored bytes and GetPixel results on a generated color/alpha grid and edge values, without image/model/data-loader dependencies.

Any resource comparison needs a separate frozen ABBA registration: same generated colors/dimensions, fresh processes, bitmap allocation outside copy timing, full output hash outside timing, managed allocation deltas and owned-process RSS/cleanup. Keep negative results and do not infer native live bytes from cumulative allocations. No measured speed assertion from concurrent functional builds. No production/fork change follows until exact pixel compatibility, meaningful allocation evidence, independent review and affected decoder regressions pass. A successful transfer helper does not remove ImageSharp or close TIFF archive validation, source-fork maintenance or advisory gates.
