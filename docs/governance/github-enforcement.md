# GitHub maintainer enforcement checklist

**Proposed setup, checked November 4, 2026.** Local branch `main` has an `origin` configured. The checked-in `.github/` contains the pull request template and no workflow, CODEOWNERS, or DCO configuration. No remote settings were inspected, and no accounts, credentials, or hosting changes were used. The checklist implements the official-project acceptance policy in [GOVERNANCE.md](../../GOVERNANCE.md) and [CONTRIBUTING.md](../../CONTRIBUTING.md).

## 1. Resolve ownership before activating review gates

- Confirm the actual default branch, release branch and tag conventions, repository visibility, plan, organization policies, and authorized identities in GitHub Settings. Limit write and settings administration to authorized people or services. Use a verified lead maintainer account and explicitly appointed reviewers. Record the scope and date of any delegation in governance.
- Add `.github/CODEOWNERS` through a reviewed change using real accounts or a visible team with write access. Cover the whole repository and explicitly protect CODEOWNERS, workflows, CI and release scripts, DCO configuration, and governance/license policy. GitHub reads the base branch's CODEOWNERS. A matching entry with several owners can be satisfied by any one of them. The lead's separate approval for policy changes still needs to be recorded. [GitHub code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).
- Appoint a second authorized reviewer before activating required independent approval for all changes. GitHub PR authors cannot approve their own PRs, so a sole maintainer will be unable to merge their own PR under a mandatory approval gate with no bypass. The current policy allows documented maintainer self-review when an independent reviewer is unavailable. Until staffing or an explicit policy decision resolves that mismatch, keep the manual procedure and report enforcement as incomplete. [GitHub required reviews](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews).

## 2. Protect branches and register actual checks

In **Settings → Rules → Rulesets**, target the default branch and the actual release branch pattern. Require pull requests, at least one approving review, CODEOWNERS review and resolved review conversations. Dismiss stale approvals on new reviewable changes. Use most-recent-push approval as an additional rule if the staffing test passes. Block force pushes and deletion. Leave the bypass list empty, including for administrators and automation. With classic branch protection, enable the equivalent no-bypass option. Require strict, up-to-date checks on the current base and integrate one PR at a time initially. Enable a merge queue only after every required check, including DCO, is proven on the actual merge-group commit. [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository) · [Required check rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) · [Merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

These are proposed stable check names. Seed them with a harmless PR, then require the exact displayed names and verified provider. Changes to the check names or trusted provider require coordinated updates to the ruleset.

| Required check | What a successful result must cover |
| --- | --- |
| `Leviathan / functional-regression` | Release build and registered C# regression/integration suites, Angular locked-dependency build and tests, and the relevant format/security checks. Capture expected suite counts and execution receipts. Use approved fixtures and verify applicable runtime targets. |
| `Leviathan / contribution-evidence` | A maintainer-controlled attestation of the exact candidate and base SHA, claim type, baseline failure or limit, candidate result, and affected regressions. For performance or broader text claims, check matched hardware/workload, frozen tolerances, reproducible before/after results and required rights/profile evidence. Document reason and scope for any inapplicable test. A PR checkbox alone cannot satisfy this check. |
| `DCO` | Every introduced commit has the contributor's valid DCO trailer. Bind the exact check to the owner-approved, independently verified GitHub App. |

- Run required workflows for all targeted PRs and every merge group if using a queue. Use a final check that evaluates the result of each needed job even when another job fails. Fail required missing, skipped, cancelled, or unexecuted suites. Keep applicability decisions in protected configuration and make them auditable. A skipped GitHub job can satisfy a required check, and skipping an entire workflow can leave it pending. [GitHub skipped-check behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).
- Set the expected provider where GitHub offers it. Binding the GitHub Actions provider identifies the app and does not identify a particular YAML workflow. Protect workflow and test configuration and use an independently controlled check provider or centrally enforced workflow where available. Keep the manual SHA-bound evidence review until the trusted publisher exists. Do not call a candidate-controlled job or same-name untrusted status equivalent to that review. [GitHub expected check source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging).

## 3. Verify DCO trust

- Approve a DCO app only after verifying its publisher, repository-only installation scope, permissions, event handling, author matching and override behavior. The standard DCO app documents a write-user override. CNCF DCO2 documents an option to disable its own override action. If using DCO2, set `allowOverrideAction: false` in protected base-branch configuration and verify a failed check cannot be manually set to pass in the actual deployment. Protect the configuration and keep organization-member exemptions and third-party sign-off remediation disabled. A provider that cannot meet the no-bypass rule must be replaced or supplemented by a trusted independent gate. [Standard DCO app](https://github.com/dcoapp/app) · [DCO2 configuration](https://github.com/cncf/dco2).
- Enable GitHub's web-commit sign-off setting as a complement. It covers web commits. Require the independent check for CLI-created commits as well. DCO sign-off is a contributor's certification. GitHub verified commit signatures are a separate control. Test the chosen merge method so contributor trailers survive and the integrator certifies any authored modifications. [GitHub commit sign-off](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-the-commit-signoff-policy-for-your-repository).

## 4. Isolate fork execution and releases

- In **Settings → Actions → General**, use restricted defaults, require workflow approval for external contributors as appropriate to repository visibility, and disable sending secrets or write tokens to forks. Keep public PR checks on disposable GitHub-hosted or equivalently isolated ephemeral runners with least-privilege tokens, no private assets or release credentials, and no persisted checkout credentials. Run untrusted code under `pull_request`. Treat PR fields as input data. Keep privileged `pull_request_target` and `workflow_run` jobs from executing untrusted PR code, caches or artifacts. Pin actions to reviewed full SHAs or use a workflow dependency lockfile, and pin reusable workflow revisions separately. [Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository) · [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use) · [Privileged PR triggers](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).
- Restrict release tag creation and mutation to the authorized release route under a separate tag rule. Validate that the exact tag commit came from the protected branch and passed required checks. Put publishing credentials in a separate protected release environment, limited to approved branches or tag patterns. Require lead-maintainer release approval, disable environment admin bypass where supported and prevent self-review when a separate eligible reviewer is available. Build release artifacts from approved source in the trusted workflow and verify digest, dependency inventory, and data/model rights. Never promote artifacts or caches directly from a PR. If the hosting plan lacks the required control, record the gap and keep publishing manual through the lead maintainer. [GitHub deployment protection](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

## 5. Verify before declaring enforcement active

The owner approves reviewer delegation, workflow and evidence-provider implementation, DCO app installation, the actual target patterns, and the release credential path. In a disposable repository or owner-authorized dry run, prove that a signed reviewed PR passes, and that missing or forged-origin checks, a skipped required suite, an unsigned commit, stale review, a changed target branch, a direct push and an unauthorized release attempt block the relevant action. Verify fork runner permissions and absence of private inputs. If enabling a queue, verify all required check results on the grouped commit. Record ruleset and check IDs, provider, tested commit IDs, outcomes and activation date. Keep manual review in effect while any required control is missing.
